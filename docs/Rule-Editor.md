# Visual Rule Editor (`asx_ruleeditor`)

A full-page React + Fluent UI v9 **web resource** that renders and edits an `asx_rule` graph.
Below: how it is built and deployed, and what was verified against a live environment. The
user-facing manual is under `docs/guide/`.

---

## 1. Loading the graph

Reads a rule's raw config records via `Xrm.WebApi` (`$expand`, full fidelity, **not** the lossy
runtime projection `asx_ReadRules`) and maps them to an in-memory `RuleGraph`. Renders WHEN
(execution + validation condition-group AND/OR trees) and THEN (ordered actions) read-only, with
condition/action summaries and table-config node names resolved from metadata already on the
records.

## 2. Web resources

Three web resources, all in the `AscentixRulesEngine` solution:

| Web resource (name) | Type | Source |
|---|---|---|
| `asx_/ruleeditor/asx_ruleeditor.html` | HTML (1) | `client/editor.html` |
| `asx_/ruleeditor/asx_ruleeditor.js` | JScript (3) | `client/dist/asx_ruleeditor.js` (esbuild bundle, ~1.1 MB minified) |
| `asx_/ruleeditor/asx_editor.css` | CSS (2) | `client/dist/asx_editor.css` (embedded font and boot shell) |

## 3. How to open it (**must run inside the app**)

> **Important (confirmed live):** in Unified Interface online the Client API (`Xrm` /
> `Xrm.WebApi`) is injected only when the web resource runs inside the app frame, and
> `ClientGlobalContext.js.aspx` does **not** restore `Xrm.WebApi`. So the raw
> `…/WebResources/asx_/ruleeditor/asx_ruleeditor.html?id=<guid>` URL **does not work standalone**:
> the page still loads, degrading to the error panel with *"The editor could not start."*, the
> message *"Xrm.WebApi is not available in this context."*, an open-it-from-the-app hint, and a
> Reload button. (Pinned live by `editorErrors.e2e`'s raw-URL case.)

The in-app deep link, also how the editor is smoke-tested:

```
https://<org>.crm<n>.dynamics.com/main.aspx?appid=<APP_ID>&pagetype=webresource&webresourceName=asx_%2Fruleeditor%2Fasx_ruleeditor.html&data=<RULE_GUID>
```

- `appid`: the id of any model-driven app in the environment (e.g. *Ascentix Rules Engine*).
- `data`: the rule's GUID; the bootstrap reads it from either `?id=` or `?data=`.

Equivalently, from app client script: `Xrm.Navigation.navigateTo({ pageType: "webresource",
webresourceName: "asx_/ruleeditor/asx_ruleeditor.html", data: "<RULE_GUID>" })`. The in-frame
launch works because the bootstrap also resolves `Xrm` from `window.parent.Xrm`.

## 4. Build & deploy

```
cd client && npm run build && cd ..
```

Then deploy three web resources into the `AscentixRulesEngine` solution and publish them:

| Local file | Web resource name | Display name |
|---|---|---|
| `client/dist/asx_ruleeditor.js` | `asx_/ruleeditor/asx_ruleeditor.js` | Ascentix Rule Builder (bundle) |
| `client/dist/asx_editor.css` | `asx_/ruleeditor/asx_editor.css` | Ascentix Rule Builder (fonts + boot shell) |
| `client/editor.html` | `asx_/ruleeditor/asx_ruleeditor.html` | Ascentix Rule Builder |

`asx_editor.css` is generated by `npm run build` and carries the embedded font and the
pre-React boot shell. Skip it and the editor loads without either.

The web-resource type follows the file extension (`.js`→3, `.html`/`.htm`→1, `.css`→2), so the
HTML host page deploys exactly like the bundle.

## 5. Module map (`client/src/editor/`)

| Module | Responsibility |
|---|---|

Pure logic is unit-tested with vitest (`client/test/editor/`); the real `Xrm.WebApi` port and React
rendering are covered by the live smoke test (this doc), per the `client/src/xrm.ts` convention.

## 6. Confirmed live (read path)

Smoke-tested in-app against rule *SAMPLE R5 Total within credit limit* (`sample_order`):

- **Renders the real graph**: rule header, the **And** group badge, the FieldComparison
  field-reference summary (`[SAMPLE Order (root)] sample_ordertotal (op 6) → sample_creditlimit`),
  and the `Block: sample_ordertotal` action. No editor console errors.
- **Enum option values** (in `model/enums.ts`) match live data: `asx_logicaloperator` And=1;
  `asx_conditiontype` FieldComparison=1; `asx_actiontype` Block=4; `asx_tableconfigtype`
  RootTable=1. (`asx_logicaloperator` Or=2 was not directly observed in sample data, but it is the
  standard pair to the confirmed And=1.)
- **OData names** (in `load/odata.ts`): every `$select`/relationship/lookup name and the
  unquoted-GUID `$filter` (`_asx_rule_value eq <guid>`) returned 200 against the live Web API.

## 7. Editing & atomic save

**New module map (`client/src/editor/`):**

| Module | Responsibility |
|---|---|
| `model/ids.ts` | Temp-id factory (`new-N`) for not-yet-saved nodes + `isNewId`. |
| `model/tree.ts` | Pure forest helpers (find/update/remove/insert/flatten) over the group/condition trees. |
| `model/reducer.ts` | Pure edit ops: rule name; group add/update/delete; condition add/update/delete; action add/update/delete/move. No `Xrm`. |
| `save/diff.ts` | `diffRuleGraph(snapshot, working)` → ordered `Operation[]` (creates parents-before-children, updates minimized to changed attrs, deletes deepest-first/children-last). |
| `save/batch.ts` | `$batch` multipart builder (one changeset, Content-ID `$N` refs) + inner-response parser. |
| `save/index.ts` | `saveRuleGraph(api, snapshot, working)`: diff → batch → outcome. |
| `metadata.ts` | Cached metadata service (tables, columns w/ `IsValidForCreate/Update/Read`, option-sets). |
| `ui/inspectors/*`, `ui/pickers/*` | Node inspectors + metadata-driven table/column/option/value pickers. |
| `ui/GraphTree.tsx`, `ui/InspectorShell.tsx`, `ui/useMetadata.ts` | Editable tree, selection-driven inspector, metadata hook. |

**Save model:** keep a pristine `snapshot` alongside the `working` graph; on **Save**, diff the two →
**one** `$batch` changeset with `@odata.bind` lookups, `Content-ID` (`$N`) for intra-batch parent refs,
and `If-Match` on the rule PATCH for optimistic concurrency; then reload. No autosave. A 412 surfaces a
"reload before saving" conflict banner and writes nothing.

**Transport:** writes and metadata reads use same-origin `fetch` (`EditorApi` extends the read-path
`WebApiPort` with `BatchApi`/`MetadataApi`); graph reads still use `Xrm.WebApi`.

### Confirmed live (write path)

Verified against the same R5 rule:

- **`@odata.bind` navigation-property names** came from each child table's
  `ManyToOneRelationships` (`ReferencingEntityNavigationPropertyName`) and corrected
  `load/odata.ts` `BIND_NAV`. All 7 best-guesses had used relationship *schema* names and were
  wrong:

  | `BIND_NAV` key | nav property |
  |---|---|
  | `groupRule` | `asx_rule` |
  | `groupParent` | `asx_parentconditiongroup` |
  | `conditionGroup` | `asx_conditiongroup` |
  | `conditionTableConfig` | `asx_tableconfig` |
  | `conditionValueNode` | `asx_ComparisonValueNode` *(PascalCase, case-sensitive)* |
  | `actionRule` | `asx_rule` |
  | `actionTargetNode` | `asx_TargetNode` *(PascalCase, case-sensitive)* |

- **Atomic create + Content-ID**: an API-level `$batch` changeset creating a group, a **subgroup**
  (`asx_parentconditiongroup@odata.bind: $1`), and a **condition** (`asx_conditiongroup@odata.bind: $1`
  + `asx_tableconfig` + `asx_ComparisonValueNode` binds) committed transactionally (`200`, inner
  `204/204/204`), then was rolled back. Proves 5 of 7 binds + the `$1` intra-batch ref.
- **ETag concurrency**: a PATCH with a stale `If-Match` was rejected `412`, with no write.
- **In-app UI pass (Playwright, signed in as a real user) on R5**: the editor mounts in the app frame
  and renders the full graph; the only console errors are Power Apps shell noise (a Graph
  avatar-photo 404, an Aria telemetry 401), **none from the editor**. Also confirmed: dirty-tracking
  (edit → "· unsaved changes" + Save enabled); **Reload** re-fetches from the server, discarding an
  in-memory edit; the rule-name edit flows through the reducer to the header; a failed save is
  caught and shown in a non-blocking banner, no crash and working state preserved.
- **Same-origin `fetch` auth, both directions.** Reads: R5 loaded in-page. Writes: the
  Save `POST …/$batch` **authenticated and reached Dataverse**, returning a server *business* fault
  rather than 401/403 (the defect below), proving same-origin write auth + the `If-Match` envelope.

- **Full in-app save round-trip: ✅ confirmed (after the plugin redeploy below).** On R5: edit the
  rule name → **Save** → `POST …/$batch` returns success, banner shows **"Saved."**,
  Save disables (dirty clears) and the new name persists; editing back + Save restores it. R5 left
  byte-for-byte as found.

> **Resolved server-side defect (was blocking rule saves; not the editor).** Saving the rule
> (e.g. a name-only PATCH to `asx_rules`) **and** creating any `asx_ruleaction` faulted `0x80040265`:
> the **deployed** `RuleRegistrationPlugin` (on `asx_rule`/`asx_ruleaction`) still read
> `asx_tableconfig.asx_parentrelationshipname`, a column since dropped from the schema. The C#
> source was already clean (`SchemaNames.TableConfig` has no such field); the deployed assembly
> predated the column drop and was **stale**. Fixed by rebuilding the Plugin (Release) and pushing
> it; rule saves and action creates verified green afterward (API + in-app).
>
> **Separate latent plugin defect (since fixed):** `TableRuleAnalyzer.Analyze(table)` (via the
> registration plugin's reconcile) throws a `NullReferenceException` when a rule on the table has an
> action with a **null `asx_actiontype`**. Reconcile re-analyzes the whole table, so such an action
> blocks *every* subsequent save/reconcile for that table until removed; recovery requires
> temporarily disabling the `asx_ruleaction` step. The editor never produces this: `addAction`
> always sets `asx_actiontype` (ShowMessage). **Fixed:**
> the loader maps a null `asx_actiontype` to 0 and `TableRuleAnalyzer` now ignores actions
> with a null/unknown action type (they count toward no step decision); covered by unit tests.

## 8. Running the Layer-3 browser tests

The Layer-3 e2e tests are **local-only**. They never run in CI, which cannot supply the reachable
DEV environment, the `az login` session and the interactive MFA login they need.

**One-time setup**, from `client/`:

```bash
npm run test:e2e:auth
```

Runs **headed**, waits for you to sign in to Dataverse (MFA included), and persists the session at
`client/e2e/.auth/state.json` (git-ignored). Setup times out at 5 minutes; re-run if it does. Later
test runs reuse the session until it expires, then re-run `npm run test:e2e:auth`.

**Prerequisites:**

- `az login` session is active (the tests use the CLI to call the Web API for throwaway-rule CRUD).
- Repo-root `.env` is configured with `DATAVERSE_URL=<your-dev-org-url>` (read by `client/test-dev/devEnv.ts` as `../.env`; the same file `npm run test:dev` uses).
- DEV is reachable; the tests create and delete rules and fail if the Web API is unreachable.

**Run the tests**, from `client/`:

```bash
npm run test:e2e
```

Runs every spec in `client/e2e/` on Chromium, then `scripts/record-live-run.mjs l3` to
record the run. Two examples:

- **`dialogA11y.e2e.spec.ts`** makes live a11y assertions on the Fluent UI modal (`aria-hidden`,
  focus trap) that jsdom cannot.
- **`authorPublish.e2e.spec.ts`** drives the author → validate → publish flow end-to-end, confirming the
  Draft → Published status-code change and persistence via real `$batch` calls.

Specs create throwaway rules under a reserved name prefix and delete them in a `cleanup()` that
runs even on failure, then navigate the editor web resource and assert against it.
